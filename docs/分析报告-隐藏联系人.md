# DYHelper「隐藏联系人」功能分析报告（不解密 payload 方案）

> 分析对象：DYHelper1.9.5.apk（Xposed 模块）+ 抖音 40.8.0 宿主包
> 日期：2026-11-21
> 方法：模块侧明文资源/字符串分析 + 抖音 dex 静态扫描（DexScan 工具，dexlib2 实现）
> 前置说明：模块的 hook 逻辑在加密 payload（assets/dyhelper/payload-0/1.dydx）内，本报告不涉及解密，全部结论来自模块明文元数据与抖音侧代码定位。

## 一、功能的输入模型（模块侧，全部明文可读）

### 1. 名单数据（用户输入）
来源：`res/values/strings.xml`（hidden_contact_*）+ `dialog_hidden_contact.xml`

| 字段/输入 | 说明 |
|---|---|
| 联系人名称 / UID | 每条名单的核心字段（`hidden_contact_item_name` / `hidden_contact_item_uid`） |
| 手动输入 UID | `hidden_contact_manual`，支持不搜索直接加 |
| 搜索选择 | "搜索昵称、群名、抖音号、UID 或会话 ID" —— 支持**会话 ID** 维度，说明名单可绑定到具体 conversation（这正对应"聊天记录入口隐藏"） |
| 加载来源 | `hidden_contact_loading`（"正在加载联系人…"）—— 添加页从抖音本地联系人/会话数据实时拉取供勾选 |
| 存储粒度 | "名单按当前账号独立保存"（footer 文案）—— 名单 key 含账号 uid 维度 |

### 2. 配置开关（`res/xml/dy_v11_catalog.xml`，key 前缀 `hidden_contacts::`）

| key | 标题 | kind | 含义 |
|---|---|---|---|
| ::0 | 启用隐藏联系人 | switch | 总开关（默认开） |
| ::1 | 是否隐藏对应横幅通知 | switch | 应用内横幅 |
| ::2 | 隐形通知（标题加粗） | switch | 不显示通知内容，仅把消息页顶部"消息"二字加粗 |
| ::3 | 加粗字重 | range | 加粗程度 |
| ::4 | 来消息震动 | switch | 隐形通知的触觉提示 |
| ::5 | 震动时长 | range(30–2000ms) | |
| ::6 | 屏蔽语音/视频通话提醒 | switch | 来电横幅/响铃 |
| ::7 | 操作面板临时显示按钮 | switch | 默认开 |
| ::8 | 临时显示时长 | entry | 临时放行窗口时长 |
| ::9 | 侧边栏同步隐藏联系人 | switch | 侧边栏同步隐藏 |
| ::10 | 联系人菜单 | entry(target=**HiddenContactDialog**) | 名单管理入口 |
| ::11 | 连点触发次数 | entry | 临时显示的触发方式 |

> ::7/::8/::11 组合即"临时显示"机制：被隐藏的联系人来消息时，可通过操作面板按指定连点次数临时显示一段时间——这是典型的"隐藏但不失联"设计。

## 二、实现架构（为什么不解密也能推断出完整链路）

1. **入口**：`MainHook`（libxposed API）按进程分发，目标包为抖音，最佳适配 41.0，兼容 40.0.0.1+。
2. **加载**：`core/protection/PayloadLoader` 用 `InMemoryDexClassLoader` 加载解密后的 payload dex（payload-0/1.dydx，合计约 8MB）；解密由 native `libdy_runtime.so` 完成，`DailyTokenSync` 做每日令牌校验。
3. **hook 点定位**：模块内置 **DexKit**（org.luckypray.dexkit），在运行时对抖音 dex 做特征搜索而非写死类名——这解释了两件事：
   - 抖音 40.8.0 里关注/粉丝列表等页面类名已高度混淆（见下文），硬编码类名根本不可维护；
   - 模块声明"最佳适配 41.0"，靠 DexKit 特征跨版本容错。
4. **UI 注入**：`dialog_hidden_contact.xml` 等 5 个隐藏联系人相关布局都在模块 APK 资源里，但模块自身 smali 无任何引用——说明设置面板/对话框代码在 payload 内、运行在**抖音进程**中（即"操作面板"），资源从模块包动态取用。配置 schema（catalog v11，共 371 个 key）也以资源形式随包分发。
5. **配置存储**：模块明文代码中无 SharedPreferences/MMKV 引用，配置读写同样封装在 payload 内（宿主数据目录下的私有存储），Xposed 跨进程读取。

## 三、抖音侧 hook 点定位（40.8.0 静态扫描 + **真机运行日志双重确认**）

> 运行期验证方式：adb 连接 vivo PLQ110 (Android 17) 抓取 LSPosed 日志，抖音 40.8.0 + DYHelper 1.9.5 实测触发。完整日志：`decode/runtime_logcat.txt`。
> 模块日志前缀 `DyHelper.DexKit.<key>` 的解析结果即运行时实际命中的 hook 点。

### 1. 消息页会话列表（"消息入口隐藏"主战场）✔ 运行时确认
- `[classes22.dex] com.ss.android.ugc.aweme.im.sdk.module.session.rips.list.RipsSessionListAdapter`
  - 关键方法：`getItemCount()`、`onBindBasicViewHolder(ViewHolder,int)`、数据提交 `LLD(List, Z)` / `LJLLLLLL(List)`
- **运行时命中**（DexKit key `hidden_contact_session_unread_methods_v1`）：
  - `com.ss.android.ugc.aweme.im.service.rips.CommonSessionItemState#LIZJ():X.0oPx`（classes22.dex，未读/状态 getter）——驱动"隐藏联系人有新消息→消息标题加粗"（::2）与来消息震动（::4）
- 数据层接口 `SessionListLogicApi`：`buildSessionListOnPhase2()` / `refreshData()` / `openConversation(String)`
- **推断**：隐藏=会话数据进入 Adapter 前按名单（uid/会话 ID）过滤；"临时显示"=叠加时间窗放行。

### 2. 横幅通知链 ✔ 运行时确认（三个 DexKit key）
| key | 运行时解析结果 | 对应配置 |
|---|---|---|
| `hidden_contact_realtime_notification_methods_v5` | `com.ss.android.ugc.aweme.im.sdk.notification.immessage.ImInnerPushManagerNew#LIZJ(MessageNotiWrapper):void`（anchor_hit，实时横幅） | ::1 横幅通知 |
| `hidden_contact_offline_notification_methods_v3` | 40.8.0 下 `offline_manager_missing candidates=4`，未命中（离线通知管理器缺失） | 离线推送横幅 |
| `hidden_contact_notification_cancel_methods_v2` | 进入 exact_stable_class 阶段，resolve 结果条件触发（通知取消路径） | 通知撤销 |
- 另有独立 hook：`im_internal_notification_methods_v4` → `ImInnerPushManagerNew#LJ(BannerInfo, Function1):void`（ImportantNotificationHook，消息页顶部重要通知）

### 3. 语音/视频通话提醒 ✔ 静态确认
- `[classes17.dex] com.bytedance.android.xrtc.notification.CallingNotificationService`（已反编译：`jadx_call/.../CallingNotificationService.java`）
- 通话入口 UI：`im.business.chat.feature.title.compoent.SingleChatCallLogic / GroupChatCallLogic`（classes22）
- **推断**：::6 在通知服务与来电横幅两层拦截；被拦截的通话仍按 ::2/::1 链路提示。

### 4. 主 Tab（"消息"标题加粗 / 底栏过滤）✔ 静态确认
- `[classes40.dex] com.ss.android.ugc.aweme.main.BaseTabChangeManager`、`TabChangeManager`
- ::2 的加粗落在主 Tab 文本渲染层，由第 1 条的未读 getter 驱动。

### 5. 关注/粉丝、搜索、分享、聊天记录 ✔ 运行日志拿到入口类
| 入口 | 类 | 状态 |
|---|---|---|
| 关注/粉丝列表 | `com.ss.android.ugc.aweme.following.ui.FollowRelationTabActivity` | **基础包 56 个 dex 中只有引用无定义**（运行时动态加载），仅运行期可解析 |
| 分享面板 | `com.ss.android.ugc.aweme.im.share.aweme.only.sharepanel.ui.SharePanelDialog` | 运行日志确认"分享面板打开"，同上动态加载 |
| 消息内搜索 | `com.ss.android.ugc.aweme.im.search.ui.v2.ImSearchActivityV2`（classes22.dex） | 静态可查 |
| 个人主页 | `MyPandaFragment`（运行日志 profile owner 生命周期可见） | |
| 聊天记录 | `im.business.chat.msgcell` 体系（cell Logic/UI 分离） | 静态确认存在 |

- **结论**：这几个入口正是模块必须打包 DexKit 的原因——页面类要么混淆要么不在基础包内，只能运行期特征解析后 hook 列表数据层按名单过滤。

## 四、如需复现：最小实现路径（全部锚点已运行时验证）

1. **数据**：模块私有存储维护 `{account_uid → set(联系人uid | conversation_id)}` 名单 + 上表 12 个开关；Xposed 侧经 XSharedPreferences/跨进程读取。
2. **消息入口**：hook `SessionListLogicApi` 实现类的列表构建（或 `RipsSessionListAdapter` 数据提交方法），按名单过滤 item；"临时显示"用时间戳窗口放行。
3. **通知链**：hook `OfflineNotificationServiceLogic` / `SingleOfflineNotificationServiceLogic`——命中名单时：横幅不渲染 → 触发 Vibrator → 通知主 Tab 加粗；::6 时再拦 `CallingNotificationService`。
4. **其余入口**（关注/粉丝/搜索/分享/聊天记录）：DexKit 以"UID 字符串渲染 + 列表 Adapter"特征搜索定位后按同样思路过滤。
5. 版本容错：全部 hook 点经 DexKit 特征解析，不写死类名。
