## 二、匹配逻辑（三层，逐级放宽）

1. **结构化匹配**（`matchAllowed`，深度 3）
   在列表项及其包装字段中寻找白名单对象：
   - `User` / `IMContact` / `CommonSessionItemState`（含子类，assignable 判断）
   - `SessionInfo` → 取 `LLIFFJFJJ()` 的 IMUser
   - `IMUser`（全混淆模型）→ 用静态转换器 `l(IMUser): User` 再匹配
   - 黑名单：`FeedStructModel`（信息流）/ `Comment`（评论区）整体跳过，防误伤
2. **getter 匹配**：`getUidS/getUid/getId` 对比 uid 集合；`getDisplayName/getNickname/getTitle` 对比昵称集合
3. **字符串兜底**（`matchByStrings`）：包装对象内任意 String 字段等于名单 uid/昵称即命中
   —— 这一层解决了 `X.0ozQ` 这类「会话行只存 uid 字符串、IMUser 为 null」的结构

## 三、配置传输（关键工程决策）

调试中验证：XSharedPreferences 在 LSPosed 上不可读（SELinux chcon 后仍失败）、
ContentProvider 因包可见性返回 null 游标。最终采用**三条通道**：

| 通道 | 方向 | 用途 |
|---|---|---|
| 广播 `com.lx.hidcontacts.UPDATE` | 设置页 → 抖音进程 | 保存即时生效（连发 3 次覆盖冷启动窗口） |
| 抖音 filesDir `xpro_hide.txt` | hook 自写自读 | 跨重启持久化（enabled + 名单） |
| ContentProvider `com.lx.hidcontacts.config` | hook → 设置页 | 补充读取（部分环境下可用） |

名单格式：每行 `uid,昵称`（逗号分隔，可只写其一）；`#` 开头为注释。

## 五、构建（本机免 Gradle 管线）

```
aapt2 link  -o build/base.apk -I android.jar --manifest AndroidManifest.xml -A assets
javac -g --release 8 -cp "android.jar;api-82.jar" -d build/classes src/**/*.java
d8 --release --lib android.jar --min-api 26 --output build/dex build/classes/**/*.class
jar uf build/base.apk -C build/dex classes.dex
java -jar uber-apk-signer.jar -a build/base.apk --out build/signed
adb install -r build/signed/base-aligned-debugSigned.apk
```

**坑位**：
- JDK21 编译的**匿名内部类**会触发旧版 d8 内部崩溃 → hook 回调一律用具名内部类
- `MatrixCursor` 存 `Boolean` 时 `getInt` 异常 → 布尔列改存字符串 `"1"/"0"`
- 链式命令里 `javac` 失败会被 `;` 吞掉 → 构建要用 `&&` 且检查产物数量

## 六、遗留项：无（8/8 全部通关）

第 8 项（直播间长按分享面板）最终定位为 `com.ss.android.ugc.aweme.feed.ui.masklayer2.OptionsDialogV2`，
通过 hook 其列表入口 `LJLLLLLL(List)` / `LJZI(List)` 与返回值 `LLFF()` 完成过滤，实测截图确认联系人消失。

### 调试经验（留给后续维护）
- LSPosed 模块日志有**配额**：高频调试日志会触发限流，之后新日志静默丢弃（表现为「功能已生效但日志不动」），此时以 UI 实测为准
- 面板类定位三板斧：`RecyclerView.setAdapter` 探针 → `LayoutInflater.inflate` 探针（带调用栈）→ `Dialog.show` 探针
- 视图会被复用/预加载：同一面板二次打开不再走 inflate，需重启进程才能再次捕获

## 七、抖音内设置面板（v3，新增）

**触发**：在抖音任意输入框（聊天框 / 搜索框）输入 `#dy` → 清空输入并弹出设置面板。
实现：hook `EditText` 全部构造函数（`hookAllConstructors`）挂 `TextWatcher`，覆盖重写了
`onAttachedToWindow` 的自定义输入框（如 `SearchableEditText`、聊天输入框）。

**面板能力**（`InAppPanel.java`，在抖音进程内用原生 AlertDialog 渲染）：
- 总开关
- 8 个功能开关：session / following / follower / search / share / mutual / skylight / invite
- 联系人勾选（数据来自好友池，自动勾选已隐藏项）
- 保存 → 写入 `xpro_hide.txt`（含 `features=` 行）并即时生效

**功能开关如何生效**：`filterList()` 按 label 映射 feature（`featureOf`），关闭即跳过过滤；
`invite`（按名字匹配的那套）在 `TextViewSetTextHook` 与 `scrub()` 中独立判断。

**好友池采集**：
- 行级：`RawFriendListItemViewHolder` 绑定时记录 uid+昵称（受可见范围限制）
- 持久化：`xpro_friends.txt`，重启后仍可选取
- 已知限制：互关 47 人只能采到约 29 人 —— 需把互关列表滑到底部一次；
  数据层钩子（MateListItemHolder.G3 / EzListAdapter.getItem / FollowerListGroupAdapter.getItemCount）
  在该页面均未命中，后续可从互关 API 响应或 Fragment 数据源切入。

## 八、v4：好友池全量采集 + 选择器增强

**问题**：好友池仅记录"行被渲染"的好友，互关 47 人只能采到约 29 人，且要求手动滑到底部。

**解决（数据层全量钩子）**：
1. `RawFamiliarFriendsAdapter.LJLLLLLL(List)` — 互关页适配器数据提交，一次收到全部 47 项
   （元素是 `X.10bQ` 包装类，经 `recordDeep` 拆包 → 字段 `a` = `profile.model.User`）
2. `RelationFetchManager.LJIILJJIL(long, RelationFetchResponse)` — **IM 关系全量同步投递点**
   （借鉴 DYhelper 的实现路线），App 启动/IM 登录即触发，无需打开任何页面；
   扫描 Response 的全部无参 List getter 采集
3. `publishFriends` 节流修复：1.5s 节流期间的更新改为延迟补发（PublishTrailing），
   批量采集完成后 `forcePublishFriends()` 强制落盘 —— 修复"47 项瞬间入表只写出第 1 项"的丢数据问题

**选择器（FriendPicker，d8 兼容要点）**：
- 搜索框过滤昵称/uid；已选置顶 + 其余按昵称 A-Z（`Collator` 简体中文拼音序，手写插入排序）
- **d8 8.2.2 已知 bug**：`Comparator<Integer>` 内访问 `List<String[]>` 会 NPE 编译失败 ——
  避免在该组合下实现 Comparator；嵌套内部类也需全部 static 化
- 面板小字：`当前已隐藏：N 个联系人 / 好友池：M 个`（M 与选择器计数一致，已移除滑动提示）

**DYhelper 逆向结论**（对照参考）：
- 业务逻辑全部打包于加密载荷（payload-*.dydx + libdy_runtime.so 解密），静态不可读
- 通过 `libdexkit` 运行时搜索 hook 目标，结果缓存在抖音侧
  `shared_prefs/dyhelper_dexkit_cache.xml`（本模块的钩子目标表可与之互相印证）
- 隐藏名单存储：抖音侧 `dyhelper_prefs.xml` 的 `hidden_contacts_v2` JSON 字符串
- 其联系人能力 = 按界面逐点 hook（RipsSessionListAdapter / IMUserRepository.getUser 等）+
  `relations.core` 关系同步数据 —— 与本模块 v4 的 RelationFetchManager 钩子同一数据源

## 九、v5：一起看-分享面板改用真实好友池 uid 精准隐藏（消除闪烁/误伤）

**旧方案的问题**：一起看邀请面板始终走"视图层文本匹配 + 行折叠"——hook `TextView.setText` /
`Dialog.show` 轮询 / `RecyclerView.onLayout` 后 `scrub()`，靠 `names.contains(TextView文本)` 判断。
三个顽疾：① 滚动重绘先显示再折叠（闪烁）；② RecyclerView 复用行恢复判断靠"子树还有没有隐藏名字"，
旧文本残留导致误伤正常联系人；③ 只能按昵称匹配，无法用 uid。

**新方案（数据层 uid 精准判断）**：
1. 定位真实适配器：启用 setAdapter spy（带 Context 归属）抓到面板联系人列表 =
   `com.ss.android.ugc.aweme.im.share.sharelist.IMShareContactsListAdapter`
   （早先误判成视频通话的 `CallingInviteFriendAdapterV2`，那套在这个面板根本不触发）。
2. hook `IMShareContactsListAdapter.onBindViewHolder(holder, int)` 及三参 payload 版本；
   after 阶段 `getData().get(pos)` 取真实 `IMContact`/`IMUser`，提取 uid → `uids.contains(uid)` 判断。
   命中即整行 GONE+0尺寸；**每次绑定先无条件 restore**，解决复用误伤。
   在 onBind 阶段拦截，早于绘制 → 零闪烁。
3. **关键坑**：`IMUser.LJJJLZIJ()` 返回的是 `initialLetter`（首字母如 "K"/"J"），**不是 uid**！
   （jadx 反编译确认 `getUid()/getUidS()/getSingleId()` 才返回 `this.uid`）
   `inviteUid()` 按类型选 getter：`IMMember` 用 `LJIJJLI()`，`IMUser` 用 `getUidS/getUid/getSingleId`，
   并要求长度≥5 才认作 uid，避免首字母误判。
4. 旧的视图层机制统一由 `VIEW_SCRUB_ENABLED=false` 关闭（代码保留可回退），避免两套打架。

**实测**：面板"最近分享"里 🌈竹溪溪（隐藏）整行消失且列表自动补位（potato 顶上）；
连续上下滑动 3 个来回 → 42 次精准折叠、无闪烁、无误伤、无空白；正常联系人完好。

**定位方法沉淀**：面板类 ≠ 适配器类；必须用带 Context 归属的 setAdapter spy 抓真实 adapter，
不能凭历史经验猜（同一个"分享/邀请"UI 在不同版本用了 sharelist / group.adapter / relations 多套体系）。

## 十、v6：全部入口统一切到 uid 精准识别（彻底移除昵称文本匹配）

**背景**：v5 只有"一起看-分享面板"走真实 uid；其余 10+ 入口仍共用 `isHidden()`，
其内部会落到 `names.contains(昵称)` 与 `matchByStrings()` 深度字符串扫描——这是同名误伤、
复用误判的根源。用户要求"其他地方也像一起看一样优化，不再用文本"。

**改造内容**：
1. 新增统一 uid 提取器 `resolveUid()`，与邀请面板同一套类型感知逻辑：
   - `IMMember` → `LJIJJLI()`；`IMUser` → 走静态转换器 `l()` 转成 `User` 后再取 uid；
   - `User / IMContact / CommonSessionItemState / SessionInfo` → `getUid/getUidS/getSingleId/getId/getSecUid`；
   - 任意包装/VO → 递归拆字段（深度 5 层，遍历集合元素），**字符串只在等于已隐藏 uid 时才认**，
     绝不匹配昵称；uid 长度 <5 一律不认（防 `LJJJLZIJ()` 首字母误判）。
2. `isHidden()` 改为纯 `uids.contains(resolveUid(item))`。`names` 仅保留用于旧配置读写兼容，
   **不再参与任何隐藏判定**；`hiddenCount()` 也改为只数 uid（面板显示与判定一致）。
3. 四个行级 hook（分享/互关单元格 `HideCellHook`、分享面板行 `HideByArgHook`、
   Skylight cell `BindItemHideHook`、在线好友头像条 `BindRowHideHook`）统一改走
   `collapseRowByUid()`：每次绑定**先恢复复用行 → 再按 uid 判定 → 命中才 GONE + 宽高 0**，
   与 v5 邀请面板同一套防闪烁/防误伤机制。
4. `ReturnListFilter` / `filterList` 的生效条件从 `uids || names` 收敛为只看 `uids`；
   旧的 `matchByStrings()` 文本匹配实现已删除（`VIEW_SCRUB_ENABLED=false` 的视图层代码保留可回退）。

**验证**：编译/签名/安装成功；日志显示全部 hook 安装正常，配置加载 `uids=3 / 好友池=52`，无异常。
各入口真实隐藏效果需配合 UI 逐页复测（消息、关注、粉丝、搜索、分享、互关、Skylight）。

## 十一、v6.1：修复误伤 + 会话/搜索按好友池 uid 反查 + App 主页精简

**用户反馈的四点**：① 消息列表隐藏失效；② 互关/关注/粉丝/朋友四个列表"不显示"（实为误伤全空），
但粉丝页搜索能搜到；③ 独立 App 主页只要功能列表；④ 功能开关文案"一起看等弹窗（按名字）"改名。

**根因与修复**：
1. **全列表误伤（严重）**：v6 的 `findUidDeep()` 在遇到白名单对象时把 `uidOfAllowed()` 的返回值
   **未经名单校验**就当命中返回（`uidOfAllowed` 只判长度≥5），导致 `isHidden()` 恒 true，
   整个关系列表被过滤成空。粉丝搜索结果 VO 结构不同没触发，所以还能搜到 —— 与用户现象吻合。
   修复：`uidFromValue()` 内白名单对象分支改为 `isHiddenUid(s) ? s : null`，必须在名单里才算命中。
2. **消息列表失效**：`SimpleSessionItemState`（会话项）只有 `id`(会话id) 与 `title`(昵称)，**没有对方 uid**，
   v2 靠昵称文本命中、v6 移除文本后彻底失效。修复：新增 `resolveUidByPool()` —— 递归扫描 VO 的字符串，
   用真实好友池 FRIENDS(uid→name) 把昵称反查为 uid，再判断该 uid 是否在隐藏名单。
   本质仍是 uid 判定，且只认"好友池里真实存在 + 已被隐藏"的昵称，抗同名误伤，不等同旧文本方案。
   接入点：`resolveUid()` 末尾兜底（findUidDeep 无结果时才走）。
3. **会话 id getter 提前返回 bug**（上一轮 v6 遗留）：`resolveUid()` 拿到第一个 uid-like 字符串
   （如会话 id）就返回，阻断对内部真实 uid 的继续查找。改为每条候选先 `isHiddenUid()` 验证。
4. **App 主页精简**：`SettingsActivity` 重写为纯只读功能列表（8 项功能名+说明），
   移除名单编辑框/好友选择/保存/广播等，所有配置统一走抖音内 `#dy` 面板。
5. 文案：功能开关 `invite` 显示名改为"一起看邀请面板"。

**验证日志**（安装重启后抓取）：
- `filtered 3 item(s) [session by RipsSessionListAdapter]` —— 消息列表过滤恢复
- `row hidden [skylight uid]=83246874906` / `[online-list uid]` —— 头像条按真实 uid 折叠
- 编译零错误、dex 79292 字节、签名安装成功。

## 十二、v6.2：粉丝搜索过滤 + 四列表开关合并

**用户反馈**：① 粉丝页搜索仍能看到隐藏联系人（主列表已隐藏）；② 功能开关里关注/粉丝/互关三项缺"朋友列表"，且要合并为一个。

**根因**：粉丝页搜索走 `SelfFollowerRelationViewModel.mB(String) -> dB(Function1) -> TA().setValue(function1.invoke(QA()))`，
是对 LiveData state 的**本地变换**，数据取自 `QA()` 的 `C214410jq`（含未过滤原始 `C162410bS.LIZ`），
**完全绕过主列表的 KA(List,C214610js,boolean) 过滤**，所以隐藏联系人被重新 setValue 带回 UI。

**修复**：
1. hook 父类 `FollowerRelationViewModel.dB(Function1)`，after 阶段调 `filterRelationState()`：
   取 `TA().getValue()` → `LJII()` 得 `C162410bS` → 读其 `LIZ` List → 按 uid `isHidden()` 原地 `removeAll`。
   一处覆盖 Self `mB(String)` 与 Other `FA/EA` 全部粉丝搜索路径。label 用 `follower-search-dB`。
2. 四列表开关合并：InAppPanel.FEATURES 与 SettingsActivity 里把"关注列表/粉丝列表/互关列表"
   合并为单行 `relation` =「关注 / 粉丝 / 互关 / 朋友列表」（补上朋友列表表述）。
   `featureOf()` 将 following/follower/mate 前缀统一映射到 `relation`；
   `isFeatureOn("relation")` 兼容旧配置里 following/follower/mutual 任一开启。

**验证**：编译零错误、dex 80432 字节、签名安装重启成功；日志 `follower-search dB hook installed`、
`filtered 2 item(s) [follower]`（主列表）。搜索过滤需用户在粉丝搜索页输入关键词后复测确认。

## 十三、v6.3：行级 hook 补开关控制 + 顶部头像条功能去除 + 搜索诊断

**用户反馈**：① 四列表合并后关闭开关，互关页仍隐藏；② 搜索/更多聊天开关关闭不恢复；

## 十五、v6.5：mutate 可逆恢复 + 粉丝搜索显式诊断

## 十六、v6.6：找到分享开关失效真正根因（base-adapter label 无归属）

**用户关键线索**：关闭总开关（enabled=false）分享页能恢复；但只关闭 share 功能开关不恢复。
这证明存在一条隐藏路径**只认总开关、不认功能开关**。

**根因**：`BaseAdapter` 的通用 hook 用的是 label `base-adapter:LJLLLLLL/LJLLI/LJLZ/LJZ`，
而 `featureOf("base-adapter:*")` **不匹配任何前缀 → 返回 null**。
`filterList()` 里 `fk == null` 时会跳过 `isFeatureOn()` 判断、直接过滤——
分享页的联系人列表正是通过某个 `BaseAdapter` 子类的 `LJLLLLLL` 设置的，
所以关 share 开关时这条通用 hook 仍照常隐藏，只有关总开关（!enabled）才停。
这也解释了粉丝搜索：`FollowerSearchAdapter.LJLLLLLL` 内部调 `super.LJLLLLLL`，
真实数据最终走 BaseAdapter.LJLLLLLL —— 同样无归属。

**修复**：`filterList()` 中当 `featureOf(label) == null` 时，改用 `featureOfOwner(param.thisObject类名)` 推断归属：
- 类名含 share/Share/picker/Picker/invite/Invite → `share`
- 含 follower/Following/mate/Mate → `relation`
- 含 session/Session → `session`
- 其余保持 null（不过滤开关，避免误伤未知页面）。
一处修复同时覆盖分享页所有 BaseAdapter 子类路径与粉丝搜索真实数据路径。

**粉丝搜索诊断**：`fs-diag size=1 types=10oM(uid=-)` —— FollowerSearchAdapter.LJLLLLLL 收到的是
X.10oM 空壳（ConcatAdapter footer/占位），真实 C241410oC 列表走 super.LJLLLLLL（BaseAdapter），

**验证**：编译零错误、dex 84036、安装重启成功；配置为手动移除 share 的干净状态

## 十七、v6.7：搜索源头 hook + 分享恢复机制重构（修复两大遗留）

**用户反馈**：① 关闭 share 开关后，分享头像条已恢复，但联系人头像仍未恢复；② 粉丝页搜索仍能搜到隐藏联系人。

### 问题②根因：粉丝搜索数据来自本地搜索源头，下游 hook 全部错过

诊断日志 `fs-diag size=1 type0=X.10oM uid0=null` 显示：`FollowerSearchAdapter.LJLLLLLL` 只收到
`X.10oM` 空壳（ConcatAdapter footer），`dB`/BaseAdapter 也拿不到真实联系人。
反编译 `SelfFollowerRelationFragment.yN()` 确认搜索数据流：
```
LocalBasicUserService.LIZIZ.LJIIIZ(keyword, scene)   ← 门面
  → LocalBasicUserServiceImpl.LJIIIZ(String, EnumC239010no)  ← 实现
    → C241510oD.LIZJ() 返回 List<C241410oC>（本地搜索缓存，元素有真实 uid 字段 LJIJ()）
```
现有全部 hook 都在下游，源头从未被过滤。

**修复**：hook `LocalBasicUserService` + `LocalBasicUserServiceImpl` 的 `LJIIIZ`（反射按方法名+参数个数 hook，
不硬编码混淆类 `X.EnumC239010no`），after 阶段对返回的 `List<C241410oC>` 按 uid 过滤，非 mutate（setResult 新表）天然可逆。
`resolveUid()` 新增 `C241410oC` 显式 getter 分支（`LJIJ()`=uid、`LJIILJJIL()`=secUid）精准识别。归属 `relation` 开关。

### 问题①根因：mutate 原地删除污染上游 + 备份恢复失效

- `share-head` 头像条走 `filterList`（非 mutate，arg 替换）→ 开关关闭立即恢复 ✓
- 联系人头像走 `IMShareContactsListAdapter` + `SharePanelViewModel.LJ()`：
  - `shvm-LJ` 用 `ReturnListFilter(mutate=true)` 原地删除上游持久 list，关闭开关后该 list 不刷新则无法恢复；
  - `LLD()` 内部 `getData().clear()/addAll()` 重建列表，备份按引用恢复易失效；
  - `ReturnListFilter` 在 drop 为空时错误 `restoreMutated`，开启态下反而把隐藏项还原（闪烁隐患）。

**修复**：
1. `shvm-LJ` 改为非 mutate（`ReturnListFilter("shvm-LJ")`），不污染上游持久数据，天然可逆。
2. `ReturnListFilter` 开启态 drop 为空时不再恢复备份；关闭态除恢复当前引用外，调用
   `clearAllMutatedBackups()` 把所有历史备份按引用写回，解决"list 引用变化恢复失效"。
3. `saveConfig()` 在关闭 share/总开关时主动 `clearAllMutatedBackups()`，涵盖"停留在页面上直接关开关"场景。

### 严重连带 bug（本次一并修复）

初版 localsearch hook 在 for 循环外 `findClass("X.EnumC239010no")`，该类在 hook 早期 classloader 找不到 →
抛异常中断整个 `installGenericHooks()`，导致**后续所有 hook（粉丝/关注/分享/邀请等）全部未安装**。
修复：① 反射按方法名 hook 绕开混淆类；② 整个块 try-catch 包裹，任何失败都不影响后续 hook 安装。

**验证**：编译零错误、dex 99104、签名安装重启成功；全部 hook 安装日志齐全
（`follower-localsearch hooks installed 2`，分享/邀请/#dy 全在）。配置为 uids=4 enabled=true，share 关闭状态待测。

## 十八、v6.8：分享头像开关归属修正 + 搜索元素识别修复 + 强诊断

**用户反馈**：v6.7 后 ① 关闭 share 开关，分享头像条恢复但联系人头像仍未恢复；② 粉丝页搜索仍能搜到。

这就是「头像条恢复、头像没恢复」的根因。邀请面板的隐藏另有独立的
`CallingInviteFriendAdapterV2.D3`（invite 开关）负责，因此把 onBind 的 `InviteBindHook` 改用
**share** 开关不影响邀请面板，且与数据层保持一致。

**修复**：`InviteBindHook.afterHookedMethod` 的 `isFeatureOn("invite")` → `isFeatureOn("share")`。

### 问题②诊断发现：搜索元素类名与 uid 识别均不匹配

v6.7 诊断日志：`localsearch-diag size=1 hit=0 type0=X.10oM uid0=null`。
- hook 命中了 `LocalBasicUserServiceImpl.LJIIIZ`，但返回元素类型是 `X.10oM`（运行混淆名），
  与反编译的 `X.10oC`（C241410oC）不同 —— **手机运行版本与反编译 dex 版本不一致**，
  导致 `resolveUid` 里 `cn.equals("X.C241410oC")`（硬编码 jadx 名、运行时永远不成立）失效，
  且 uid 字段 getter 未命中 → uid0=null、hit=0 → 搜索名单无法过滤。

**修复**：
1. `resolveUid` 的类型判断改为按运行时混淆名特征匹配：`cn.startsWith("X.10o") || cn.contains("C241410oC")`，
   getter 扩充 `LJIJ/LJIILJJIL/LJIIJ/getUid/getSecUid/getUidS`。
2. 增强诊断：localsearch-diag 增加 `kw`（搜索词）、`poolSize`、`uids`、`dump=`（元素全字段递归 dump），
   一轮即可定位 uid/昵称真实藏匿位置，避免反复盲改。

**验证**：编译零错误、dex 100672、签名安装重启成功，全部 hook 安装齐全。待用户实测粉丝搜索 +

## 技术栈澄清：dex 解析 / DexKit / 硬编码 hook（务必区分）

> 当前模块包名 `com.secret.dyhide`（文档开头沿用旧名 `com.lx.hidcontacts`）。

本项目容易被「dex 解析」「dexkit」混淆。实际上有三层完全不同的东西：

| 层次 | 工具 / 手段 | 运行时机 | 是否打包进 dyhide APK |
|---|---|---|---|
| 开发期静态逆向 | `D:/AI/tools/dexsql.exe`（SQL 查 dex 的类/方法/字段/字符串引用）+ `jadx`（反编译抖音与抖X） | 开发时手动执行 | ❌ 否，只产出结论 |
| dyhide 运行期 | **硬编码 hook 点**：类名 + 方法名/参数个数，Xposed `findAndHookMethod` + try/catch 逐项安装 | 模块注入抖音后 | ✅ 是，但无 dex 解析代码 |
| 抖X 运行期（参照） | **DexKit / libdexkit**：运行时按语义名（`cards_kmp`/`flow_set`/`tabs`/`pager_bind`）扫描 dex 特征定位真实成员 | 抖X 模块运行时 | 仅抖X 依赖 |

源码证据：`MainHook.java` / `CompatCheck.java:44` 明确注释——

> dyhide 不使用 DexKit：所有 hook 点在 MainHook 里以「类名 + 方法名/参数个数」硬编码，再靠 try/catch 逐项安装。

「适配检测」（CompatCheck）的本质：用宿主 ClassLoader 反射验证这些硬编码目标在当前抖音版本里是否仍存在，属于**兼容性自检**，不是 dex 特征扫描。第八章第 135 行提到的 `libdexkit` / `dyhelper_dexkit_cache.xml` 是隔壁 DYhelper 的实现，与 dyhide 无关。

代价对比：抖X 用 DexKit 换版本可自动适配，但引入 so 依赖与运行时扫描开销；dyhide 硬编码轻量，但抖音大版本更新后需重新用 dexsql/jadx 逆向并改 APK。

**v16 起的变化**：dyhide 新增了 **dex 特征扫描**（`DexFeatureScanner.java`），但用的是 **dexlib2**（纯 Java 库，smali/baksmali 同款），不是 DexKit，也没有 native so。它只在「适配检测」触发时运行，按稳定特征（字符串常量/字段引用/方法签名）重新定位混淆类，把「语义名 → 当前真实类名」展示在检测弹窗里。这让版本更新后的适配从"盲猜逆向"变成"直接看到新类名"。构建链相应引入 dexlib2+util+guava+jcommander 4 个 jar（APK 约 1.8MB）。详见文末 v16 章节。

**阶段一（v16）**只做「扫描 + 展示 + 导出日志」，不自动替换 hook 目标；**阶段二（v17，已完成）**在阶段一基础上把扫描结果落盘为 `dexmap.txt`，MainHook 启动时按语义名读取真实类名替换硬编码点，并保留硬编码兜底。详见文末 v17 章节。

## v16（2026-11-25）：dex 特征扫描（版本更新自动适配辅助）

### 目标与结论
让版本更新后的适配更方便：模块在「适配检测」时扫描宿主 dex，按稳定特征重新定位混淆类，直接把「语义名 → 当前真实类名」展示给维护者，把适配从"盲猜逆向"变成"看结果改配置"。

### 选型踩坑
- 最初手写 dex 二进制解析器（header/string_ids/class_data/code_item），遇到隐蔽偏移 bug：class_data 解出的 codeOff=4582 指向 string_ids 区而非 code_item；用 Python 独立实现交叉验证得到相同错误，确认是抖音 dex 的复杂性（加固/map 重排等），手写解析器是深坑。
- **改用 dexlib2**（`D:/AI/tools/dexlib2-2.5.2.jar`，smali/baksmali 同款）：纯 Java、class 版本 52(Java8)、不依赖 `java.nio.file`、不依赖 `android.*`，Android 可跑。PC 实测扫描结果与 dexsql 完全一致。

### 实现
- 新类 `DexFeatureScanner.java`：三类特征 `byString`（字符串常量）、`byFieldType`（字段引用）、`byMethods`（方法签名组合）；`defaultFeatures()` 配 6 条规则。
- `CompatCheck` 接入（阶段一，零风险）：`init` 存宿主 `sourceDir`；`CheckTask` 后台跑 `runDexFeatureScan()`；结果弹窗新增「dex 特征扫描（自动适配）」区块；导出日志含扫描结果。
- 构建链：javac / D8 的 classpath 增加 dexlib2 + util + guava + jcommander 4 个 jar，一起打进 classes.dex（225KB → 3.3MB，APK 1.8MB）。

### 6 条默认规则（PC 与真机均 6/6 命中）
| 语义名 | 特征类型 | 当前定位 | 特征 |

## v17（2026-11-26）：阶段二动态类名 + 全程适配日志 + 防误触

### 目标（用户三诉求）
1. **阶段二**：抖音更新后，用 dex 扫描到的新类名自动替换 MainHook 里写死的短混淆类名，免改源码/免重编译。
2. **全程日志**：无论适配成功还是失效，都要有可查日志——失效时能看到「哪个类的解析出了问题」，成功时能看到「这次更新了哪个类」。
3. **防误触**：点「重新适配检测」后要有反馈，加二次确认。

### 关键代码事实（决定了实现方式）
- `X.16mc` 在 MainHook 里**没有硬编码**：CardEntry 的 flow 实现类是运行时从字段类型动态发现的（`KmpViewModelBindHook` → `hookFlowSetValueImpl(flow.getClass())`）。所以 `stateflow_impl` 这条扫描规则不对应任何硬编码点，无需动态替换。
- 真正写死、且有扫描规则支撑的短混淆类名共 **5 个**：

| 语义名（DexFeatureScanner） | 硬编码点 | 功能 |
|---|---|---|
| `profile_tab_manager` | `X.1010` | 个人页标签逐个隐藏 |
| `search_result_model` | `X.10js` | 粉丝/关注列表 KA 参数 |
| `im_search_source` | `X.0p04` | IM 搜索源状态层 |
| `load_state` | `X.0ozx` | 搜索加载状态模型 |
| `user_comparable` | `X.07WK` | 互关页排序比较器 |

- 另有 `X.07WO`、observer 批次（`X.10bM/N/O`、`X.10aV/W/X`、`X.10G2`）**无扫描规则** → 保持硬编码，但记录安装日志（失效时能看到）。
- **时序关键**：hook 安装在 `handleLoadPackage`（抖音启动最早），dex 扫描在 `MainActivity.onResume`（宿主已启动后）→ 扫描结果**必须先落盘**，下一次启动才能被 MainHook 读取。

### 实现

**① 新增 `DexClassMap.java`**（纯 Java 8 / 无 android 依赖 / 内部 class 全 static，规避 D8 匿名类 NPE）
抖音私有目录 `dyhide/` 下三个文件：

| 文件 | 写入时机 | 内容 | 策略 |
|---|---|---|---|
| `dexmap.txt` | 每次 dex 扫描完成 | `语义名=真实类名` 映射表 | 覆盖写 |
| `hooklog.txt` | 每次抖音启动、hook 装完 | 每个 hook 点的语义名/兜底类名/实际用名/来源 | 覆盖写（本轮） |
| `adapt_log.txt` | hook 安装 + 每次扫描 | 带时间戳的适配历史、类名变化 diff、扫描错误 | 追加写 |

对外 API：`load()` / `resolve(key, fallback)` / `isDynamic()` / `recordHook()` / `flushHooks()` / `saveHits(hits, ver)` / `recordScanError()` / `readHookLog()` / `formatForExport()`。
**兜底原则**：`dexmap.txt` 不存在、读失败、或某语义名没命中 → 一律用硬编码类名，模块整体永不因映射失效。

**② `MainHook.java`**
- `handleLoadPackage` 开头 `DexClassMap.load()`，末尾 `DexClassMap.flushHooks(hostVersion)`。
- 5 个动态点改为 `resolve(语义名, "X.xxxx")` + `recordHook(...)`；2 个静态点（observer、互关记录项）只 `recordHook()` 记录 OK/FAIL。
- 新增广播 `ACTION_RECHECK`：面板在 `sandboxed_process0` 子进程，而 `LAST_ACT`（MainActivity）只在主进程——原来面板直接调 `CompatCheck.rerun()` 会因 `a == null` 静默失效。现改为面板发广播 → **主进程 receiver 收到后再执行 rerun**，这是「点了没反应」的根因修复。
- 提供 `requestRecheck(Context)` 供面板调用。

**③ `CompatCheck.java`**
- `runDexFeatureScan()` 成功后调 `DexClassMap.saveHits()`（落盘 + 写 diff），失败调 `recordScanError()`。
- 结果弹窗新增 `adaptDiagView()`：**每个 hook 点当前类名 + 是否动态命中 + 功能自测提示 + 类名变化 diff**。
- 导出日志加入 `DexClassMap.formatForExport()` 完整适配历史；**「导出日志」按钮改为始终显示**（原来仅失败时显示）。

**④ `InAppPanel.java`**
- `RecheckClick` 改为二次确认弹窗（`AlertDialog.Builder` + 标题/说明 + 「确定开始」/「取消」），具名类 `RecheckConfirm` / `RecheckCancel`。
- 确认后调 `MainHook.requestRecheck(ctx)` 发广播，不再直接调 `rerun()`。

### 日志长什么样（真机抓取示例）
```
== hooklog.txt ==
[ OK ] 搜索结果模型(KA参数) | fallback=X.10js used=X.10js src=DEXMAP
[ OK ] 个人页标签管理        | fallback=X.1010 used=X.1010 src=DEXMAP
[ OK ] 观察者采集(静态)      | src=HARDCODE
[ OK ] 互关记录项(静态)      | src=HARDCODE

== adapt_log.txt ==
00:14:54 SCAN → 6 条映射落盘 + diff「6 条新增」
00:15:11 HOOK → 5 点 src=DEXMAP（重启后动态生效）
```
`src=DEXMAP` 表示用了扫描映射、`src=HARDCODE` 表示兜底硬编码；`fallback=旧类名 used=新类名` 精确记录「哪个类被换成了哪个」。

### 真机验证（已通过）
抓取文件：`dyhelp/logs/v17_capture.txt`、`dyhelp/logs/v17_verify.txt`。完整闭环验证成功：
1. 首次启动（无 `dexmap.txt`）→ 7 个 hook 点全部 `src=HARDCODE` 兜底。
2. 适配检测跑完 dex 扫描 → 写 `dexmap.txt`（6 条映射）+ `adapt_log` 记 diff。
3. 重启后 → 5 个动态点全部 `src=DEXMAP`，2 个静态点保持 HARDCODE，7/7 OK。

> 已知限制（非功能问题）：二次确认弹窗与跨进程广播修复**未做 GUI 点击实测**（WiFi adb 的 mDNS 频繁掉线），但代码逻辑与编译已验证；确认弹窗是标准系统 AlertDialog。日志里 `host=?(400801)`——`ApplicationInfo` 只有 `versionCode` 没有 `versionName`，versionCode 已足以唯一标识版本。

### 抖音更新后如何修复（v17 行为）
更新抖音后打开面板 → 「重新适配检测」，看结果弹窗的诊断区块 + 导出日志：

| 情形 | 表现 | 需要做什么 |
|---|---|---|
| **类名变了**（最常见） | 扫描命中，日志显示 `fallback=X.1010 used=X.2abc src=DEXMAP` | **什么都不用做**，重启抖音即自动用新类名。 |
| **特征字符串被改** | 扫描 MISS，`adapt_log` 记扫描错误 | 改 `DexFeatureScanner.defaultFeatures()` 规则后重编译。 |
| **hook 逻辑失效**（签名/数据结构变） | 扫描 OK，但功能没生效 | 重新逆向改 MainHook。适配检测看不出来，只能功能自测。 |

**所有 hook 回调都有 `try/catch(Throwable)` 兜底**（46 个 hook 类全覆盖），所以 hook 失效的表现是**功能静默失效，不会闪退**，抖音可正常使用。
